# Wedding Card 개인키 파일 잠금

2026-11-15. 사용자 확정 방식: **비밀번호를 받지 않고 개인키 파일만 선택하여 열기**.

## 구성

- GitHub에는 RSA 3072비트 공개키와 암호화된 콘텐츠만 저장해요.
- 개인키는 표준 PKCS#8 PEM 파일이며 별도 비밀번호가 없어요. 파일 자체가 접속 수단이에요.
- 개인키 파일은 사용자의 기기에 보관하고 저장소·배포물에 포함하지 않아요.
- 페이지에서 개인키 파일을 선택하면 ArrayBuffer를 Worker로 전달해요. 서버로 업로드하지 않아요.
- 개인키는 추출 불가능한 CryptoKey로 가져오고, 콘텐츠 키를 풀어 사진과 개인정보를 인증해요.
- 새로고침이나 탭 종료 후에는 파일을 다시 선택해요. localStorage/sessionStorage/cookie에 키를 저장하지 않아요.

## 암호화 포맷 v3

사진과 개인정보는 무작위 AES-256-GCM 콘텐츠 키로 암호화해요. 콘텐츠 키는 RSA-OAEP /
SHA-256 / MGF1-SHA256으로 공개키에 감싸고, `WeddingCard v3 content key`를 OAEP label로 사용해요.
사진 전체를 RSA로 직접 암호화하지 않아요.

| 항목           | 값                                                              |
| -------------- | --------------------------------------------------------------- |
| 공개키         | RSA 3072비트, e=65537, SPKI PEM                                 |
| 개인키         | RSA 3072비트, PKCS#8 PEM, 비밀번호 없음                         |
| 콘텐츠 암호화  | AES-256-GCM, 파일마다 CSPRNG 12바이트 IV, 128비트 인증 태그     |
| 키 포장        | RSA-OAEP-SHA256, CSPRNG 32바이트 콘텐츠 키                      |
| manifest       | 버전 3, 알고리즘, 공개키 SHA-256 지문, 포장한 키, 이미지 경로   |
| 각 암호화 파일 | `WCP3` + 12바이트 IV + 암호문·태그                              |
| AAD            | 버전·알고리즘·키 지문·포장한 키·전체 이미지 목록·해당 파일 경로 |

모든 콘텐츠와 사진 18개의 인증이 성공한 뒤 기존 카드를 시작해요. 오인증·형식 오류·파일 치환·변조는 실패하며 평문/구형 포맷 폴백은 없어요.

`objectinitializer`, `mainscene`, `mapview`, `directions`의 기존 소스는 content.bin 내부에만 있어요.
Viewer.js는 기존 1.3.7 버전을 자체 호스팅해 외부 스크립트 요청을 없앴어요.
이미지 Blob URL은 뷰어가 계속 사용할 수 있도록 페이지 종료 때 해제해요.

## 데이터 전환 및 검증

과거 콘텐츠와 사진 18개는 이미 현재 공개키 방식으로 전환해 원본 바이트까지 검증했어요.
이번 이력 정리본은 이전의 평문 파일·공개 복호화 키·사진 버전을 제거하고 현재 암호문과 공개키는 그대로 보존해요.
삭제한 과거 커밋을 이용한 최초 복원 기능은 제거했어요. 현재 암호문의 검증과 새 키 쌍으로의 회전 기능은 유지해요.

- 전체 자동 테스트: 75개 파일 / 381개 통과(초기 전체 실행 기준).
- 올바른 키·다른 키·공개키만 입력·빈 키·변조·파일 치환·키 회전 검사 통과.
- 실제 소스와 빌드 산출물의 허용 목록·키 지문·암호문 헤더·IV 중복·검증 후 변경 여부 검사 통과.
- 실제 콘텐츠·사진 18개 원본 바이트와 복호화 결과 일치.
- 린트, 전체 빌드, 기존 아카이브 참조 검사 통과.
- 브라우저에서 실제 개인키 파일 선택, 실제 카드 초기화, 갤러리 이미지 12장 로드, 드래그 확인.
- 실제 Android/iOS 기기 검증은 별도로 남아 있어요.
- 전체 format:check는 기존 파일 156개의 포맷 차이로 실패했어요. 변경 파일만 별도로 포맷 검사해요.

`protected/verified.json`은 개인키로 왕복 인증을 마친 파일들의 SHA-256 목록이에요.
CI는 형식과 해시를 검사하지만 개인키를 보유하거나 AES 인증 태그를 직접 검증하지 않아요.
키 없는 CI에서 복호화 성공을 주장하지 않아요.

## 로컬 검증과 키 교체

개인키 파일은 저장소 밖에 두세요. 명령에는 키 내용 대신 **파일 경로**만 넣어요.

```bash
npm run wedding:verify -- /path/to/weddingcard-private.pem
npm run wedding:check
npm run lint
npm test
npm run build
```

새 키 쌍으로 바꾸려면 새 개인키도 PKCS#8 PEM으로 만들고 다음을 실행해요.

```bash
npm run wedding:rotate -- /path/old-private.pem /path/new-public.pem /path/new-private.pem
```

회전 도구는 기존 키로 복원한 모든 콘텐츠를 새 콘텐츠 키로 재암호화하고, 새 개인키로
원본 바이트까지 검증한 뒤 폴더를 교체해요. 새 공개키를 `security/public-key.pem`으로
복사하고 `config/weddingcard-public-files.json`에서 그 파일의 SHA-256만 검토·갱신한 뒤
검사와 빌드를 실행하세요. `protected/`와 공개키·허용 목록을 같은 커밋으로 반영해요.
암호문만 부분 교체하면 인증에 실패해요.

## 남은 위험과 이력 정리

개인키 파일은 비밀번호 없이 사용하는 접속 수단이므로 파일을 가진 사람은 카드를 열 수 있어요.
PEM의 Base64 표현은 암호화가 아니며 난독화에 보안을 의존하지 않아요. 개인키 분실·유출 시
새 키 쌍으로 교체하세요. 이미 내려받은 암호문과 유출된 기존 개인키 조합까지 회수할 수는 없어요.
브라우저에서 열린 콘텐츠의 저장·복사도 막지 못해요. JavaScript와 GC 메모리의 물리적 완전 삭제를
보장하지는 않아요. 저장소/배포 권한 탈취 시 악성 페이지로 교체되는 위험은 별개예요.

구형 사진은 복호화 키와 함께 과거 Git 기록에 공개되어 있었으므로, 과거 자료는 이미 공개된
것으로 취급해요. 이번 변경은 현재 트리와 새 배포를 보호하며 과거 커밋·PR diff·fork·외부
캐시·기존 Pages artifact를 회수하지 않아요. 기록 강제 재작성과 영구 삭제는 실행하지 않았어요.

별도 사용자 승인 후 진행할 정리 계획은 다음과 같아요.

1. 사용자 로컬에 필요한 원본과 새 개인키를 백업해요.
2. 과거 브랜치·태그·PR·Actions/Pages artifact의 노출 범위를 조사해요.
3. 이력 정리 범위를 확정한 뒤 `git filter-repo`와 승인된 강제 push를 진행해요.
4. 재클론을 안내하고 필요하면 GitHub 지원에 민감 자료 캐시 삭제를 요청해요.

## 키 파일 오류 안내 보완

운영 암호문과 전달한 최신 개인키의 지문·전체 콘텐츠·사진 18개 인증이 일치하는 것을
재검증했어요. 키를 교체하거나 콘텐츠를 재암호화하지 않았어요. 사용자 기기에서 실패한
정확한 원인은 오류 메시지와 선택한 파일을 확인해야 구분할 수 있어요.

ZIP·공개키·예전 비밀번호 있는 개인키·잘못된 개인키·네트워크·암호문 인증·Worker 시작 실패를
서로 다른 안내로 구분해요. 모바일 파일 선택기의 확장자 필터 대신 선택 후 파일 헤더를
확인하고, 입력 내용이나 키를 로그에 출력하지 않아요. Worker 생성 실패도 잡아 버튼을 다시
활성화하고 네트워크 요청에는 20초 제한을 적용해요. JS/Worker/암호화 모듈 경로의 버전을
명시해 이전 캐시와 섞일 가능성을 줄였어요. 관련 회귀 검사 8개와 린트·빌드를 통과했어요.

## 이력 정리본의 반영 상태

정리본은 작성자·작성 시각·커미터·커미터 시각·부모 관계를 보존하여 574개 커밋을 재작성했어요.
Git 서명은 재작성 과정에서 무효화되므로 제거됐어요. 현재 Wedding Card 파일 74개는 바이트 그대로 보존했고,
과거 프로젝트 파일 버전과 루트/pixiproj에 복사된 관련 이미지도 정리했어요.
외부 참조·캐시·PR 내부 참조·이전 Actions artifact는 별도로 정리해야 해요.

이 기록은 로컬 정리본의 검증 결과이며, GitHub 반영 완료를 의미하지 않아요.
기존 기록을 가진 다른 복사본에서 merge/push하면 다시 유입될 수 있으므로 정리 반영 후 재클론해야 해요.

## 2026-11-16 보안 보완

키 선택 화면은 최상위 탭에서만 활성화해요. HTML body의 hidden 속성은 최상위 문맥
검사가 끝날 때까지 유지하고, iframe 안에서는 초기화를 중단하며 파일 입력 DOM을 제거해요.
스크립트가 차단된 sandbox 프레임에서도 입력 화면은 숨겨진 상태로 남아요.
이 검사는 보조 방어이며 HTTP `frame-ancestors` 헤더를 대신하지 않아요.
GitHub Pages에는 사용자 정의 응답 헤더 설정이 없으므로, 브라우저 수준의 프레임 삽입
차단에는 별도 프록시 또는 헤더를 지원하는 호스팅이 필요해요. CSP meta에
`frame-ancestors`를 추가해도 적용되지 않아요.

개발·미리보기 서버는 기본적으로 127.0.0.1에서만 열려요. 모바일 검수가 필요할 때만
신뢰하는 네트워크에서 `npm run dev -- --host 0.0.0.0`으로 명시적으로 열어요.

CI 기본 권한은 읽기 전용이고 Pages/OIDC 권한은 deploy 작업에만 있어요.
Uriel 데이터 수집·테스트는 읽기 권한으로 실행하고, 검증된 CSV만 불변 artifact ID로
별도 commit-data 작업에 전달해요. 쓰기 작업에서는 npm 설치나 저장소 코드를 실행하지
않고, 검증에 사용한 커밋 위에 CSV 하나만 커밋해요. 원격이 앞서 있으면 강제 push
하지 않고 실패해요. 저장소 checkout 자격 증명은 유지하지 않아요.

ESLint 파서의 minimatch는 upstream 의존성 범위가 아직 취약한 10.x에 머물러 있어
`@typescript-eslint/typescript-estree`에 한해 11.0.8로 override해요. 같은 `minimatch()`
API를 사용하는 것을 확인하고 lint로 검증해요. upstream이 안전한 버전을 사용하면
이 override를 제거할 수 있어요.
