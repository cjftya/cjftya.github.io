# Jelly Oasis — 렌더링 최적화 v1 검증 기록

기준: `f55b0fec35267c8d73568fb8b78385aa37612ab5`, 2026-10-20.

## 반영 내용

- 별도 색 보정 ShaderPass를 OutputPass 내부로 통합했어요. 기존과 같이 scene-linear HDR 색 보정 → tone mapping → sRGB 순서로 처리해요. Three의 노출·색공간 처리를 그대로 사용해요.
- 최종 화면 출력 뒤의 불필요한 composer 버퍼 교환을 생략했어요. 다른 패스가 교환된 버퍼를 소비하지 않아, 두 번째 HDR/MSAA 타깃의 GPU 할당이 필요하지 않아요.
- 디버그 통계를 프레임 전체로 수정했어요. 기존 `calls: 1`은 마지막 OutputPass만 집계한 값이었어요. 이제 수면 compute·그림자·반사·굴절·후처리를 포함하고, `renderPasses`와 `renderCountersScope`도 제공해요. 프로덕션에는 디버그 API를 노출하지 않아요.

해상도, Bloom 강도, 그림자 품질, 호수 갱신 주기, 오브젝트 밀도와 바람·수면 시뮬레이션은 유지했어요.

## 측정 결과와 범위

환경: Chromium 153, ANGLE/SwiftShader 소프트웨어 WebGL, DPR 1, Three 0.185.1. 모바일은 터치/뷰포트 에뮬레이션이에요. 실제 휴대폰 또는 하드웨어 GPU 성능 수치로 사용할 수 없어요.

기본 구도·10시·맑음·시간 정지·자연 애니메이션 활성 상태에서 웜업 후 각 30초 이상, 3회씩 측정했어요. 프레임 전체의 GL draw 명령을 직접 계수했어요.

| 지표                                 |   변경 전 |   변경 후 |
| ------------------------------------ | --------: | --------: |
| PC 캡처 프레임 draw calls            |       429 |       428 |
| PC 캡처 프레임 framebuffer bind 명령 |        37 |        33 |
| 모바일 캡처 없는 프레임 draw calls   |       214 |       213 |
| 모바일 캡처 포함 프레임 draw calls   |       425 |       424 |
| 할당된 텍스처 수                     |        23 |        22 |
| 기본 구도 geometry 수, PC / 모바일   | 109 / 108 | 109 / 108 |

Framebuffer bind는 GL 명령 수이며 렌더 패스 수와 같은 의미가 아니에요. Reflection/Refractor 캡처는 두 패스가 한 쌍이에요.

동일한 HDR 입력으로 색 보정+출력 부분만 별도 측정했어요. `EXT_disjoint_timer_query_webgl2`를 사용하고 완료를 비동기로 확인했으며 disjoint 결과는 허용하지 않았어요. 워밍업 후 전후 순서를 바꿔 3회, 회당 12번 처리한 GPU 시간의 중앙값이에요.

| 후처리 입력 크기 | 기존 두 패스 | 통합 한 패스 | 비용 감소 |
| ---------------- | -----------: | -----------: | --------: |
| 1440×900         |      48.39ms |      19.05ms |     60.6% |
| 390×844          |      12.65ms |       5.23ms |     58.6% |

**위 개선율은 해당 후처리 부분의 소프트웨어 GPU 측정치예요. 전체 장면 FPS 향상률이 아니에요.**

전체 프레임 시간은 변동이 컸어요. 최초 3회 측정의 p50/p95 중앙값은 PC 2666.6/5166.5→2533.2/4083.2ms, 모바일 633.2/1166.7→666.7/1366.7ms였어요. 모바일 악화 여부를 확인하기 위해 30초씩 다시 비교했을 때는 516.6/1249.9→483.3/1150.0ms로 방향이 바뀌었어요. 따라서 전체 FPS 개선 또는 악화를 이번 환경에서 확정하지 않았어요. 실제 기기에서 확인해야 해요.

## 화면·복구 검증

- 1440×900, 1920×1080, 390×844, 844×390의 낮·황혼·밤·비·안개와 PC/모바일의 호수·세계수 근거리, 총 24쌍을 비교했어요.
- 카메라·환경·애니메이션 시계를 고정했어요. 모든 쌍의 최대 채널 차이는 8비트 기준 1/255였고, 평균 절대 차이는 0.0071~0.0104/255였어요. 중간 HalfFloat 저장 단계 제거에 따른 작은 반올림 차이 범위예요.
- HDR 그라데이션에서도 ACES/Linear tone mapping과 night 0/0.5/1, 두 해상도의 12가지 조합을 비교해 최대 1/255를 확인했어요.
- 각 뷰포트에서 3회 재배치 후 텍스처·geometry 수가 증가하지 않았어요.
- PC/모바일의 BFCache 복귀 이벤트와 실제 `WEBGL_lose_context` 손실·복구 후 렌더링·호수 캡처가 재개됐어요. 페이지/셰이더 오류는 없었어요.

대표 비교: [밤·호수 전후 화면](../artifacts/jelly-oasis/performance-v1/visual-comparison.jpg).

## 자동 검사와 일반 재생

`npm run build`, `npm run lint`, `git diff --check`를 통과했어요. 전체 테스트는 `npm run test -- --maxWorkers=2`로 69개 파일·341개 테스트가 통과했어요. 테스트 삭제나 타임아웃 변경은 없어요.

최종 프로덕션 빌드의 PC/모바일 일반 재생에서도 바람·수면 시간 진행, 나무의 실제 움직임, 동작 줄이기 설정에서도 바람 유지, 낮·황혼·밤·비와 하늘 시점, 디버그 API 비노출을 확인했어요. 페이지·셰이더 오류는 없었어요. 단일 프로세스 소프트웨어 브라우저의 긴 지연 때문에 다중 프로세스 설정으로 검증했고, 기존 세 가지 프로세스 옵션은 선택 가능한 환경 변수로 남겼어요.

## 보류한 최적화

호수의 카메라 변화 임계값, 갱신 횟수 제한, 수면 substep, shadow caster 선별, 로딩 동시성은 바꾸지 않았어요. 현재 프러스텀 컬링·고정 시간 적분·인스턴싱·단일 그림자 광원 구조를 유지했어요. 이 환경에서는 각 변경의 실제 기기 이득과 시각적 안정성을 입증하지 못했어요. 추가 FPS 확보의 우선순위는 실제 기기의 전체 프레임 GPU 프로파일로 결정해야 해요.

## 재현

변경 전 빌드를 별도 디렉터리에 보관한 뒤 동일 환경에서 아래 스크립트를 실행해요. 기본은 브라우저의 GPU 설정을 사용하고, 소프트웨어 비교가 필요할 때만 `OASIS_QA_SOFTWARE=1`을 지정해요. `OASIS_QA_BROWSER`는 설치된 Chromium 실행 파일 경로예요. 결과와 원본 캡처는 기본적으로 `/tmp`에 저장돼요.

```sh
npm ci
npm run build
node scripts/oasis-performance-qa.mjs
node scripts/oasis-output-qa.mjs
node scripts/oasis-performance-visual-qa.mjs
node scripts/oasis-fantasy-sky-qa.mjs
```

- `OASIS_PERF_DIST`: 성능 측정 대상 빌드 디렉터리. 기본 `dist`.
- `OASIS_PERF_BASELINE`: 화면 비교용 이전 빌드. 기본 `../oasis-baseline-dist`.
- `OASIS_PERF_SECONDS`, `OASIS_PERF_RUNS`: 기본 30초, 3회.
- `OASIS_PERF_MOBILE_ONLY`, `OASIS_PERF_DESKTOP_ONLY`: 한 종류의 뷰포트만 측정할 때 사용해요.
- 기존 하늘/자연 재생 QA도 소프트웨어 모드의 기본값을 다중 프로세스로 정리했어요. 기존 단일 프로세스가 필요한 환경에서는 `OASIS_QA_SINGLE_PROCESS=1`을 지정해요. 검증 항목과 타임아웃은 유지했어요.

실제 모바일 확인은 Galaxy Fold 등의 같은 브라우저·화면 방향·시간·날씨·카메라에서 웜업 후 30초×3회 수행해요. 프레임 시간과 열/전력 영향을 함께 확인하고, 데스크톱의 모바일 에뮬레이션 결과와 분리해요.
